```rust
pub struct Attachment {
    pub id: String,
    pub title: String,
    pub _type: Option<String>,
    pub extensions: Option<AttachmentExtensions>,
    pub _links: Option<AttachmentLinks>,
    pub version: Option<AttachmentVersion>,
}

pub struct AttachmentExtensions {
    #[serde(rename = "mediaType")]
    pub media_type: Option<String>,
    #[serde(rename = "fileSize")]
    pub file_size: Option<u64>,
}

pub struct AttachmentLinks {
    pub download: Option<String>,    // path-only, e.g. "/download/attachments/123/file.pdf?..."
    pub webui: Option<String>,
}

pub async fn list_attachments(client: &Client, page_id: &str) -> Result<Vec<Attachment>, AppError>;
pub async fn download_attachment(client: &Client, download_path: &str, dest_path: &Path) -> Result<u64, AppError>;
pub async fn add_attachment(client: &Client, page_id: &str, file_path: &Path) -> Result<(), AppError>;
```

Endpoints used:
- `GET /rest/api/content/{id}/child/attachment?limit=50` (list_attachments)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ccli (local) → Confluence DC 9.2.13 | All response data is untrusted external input; serde must defensively parse. |
| Local FS → ccli `attachment add` | User-supplied file path; ccli reads contents and forwards via multipart. |
| ccli `attachment get` → Local FS | Server-supplied bytes are written to a user-specified local path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-17 | Tampering | src/api/attachment.rs serde parse | mitigate | All struct fields stay `Option<T>`; new fields if added must follow Option + serde(default) rule. |
| T-05-18 | XSRF | add_attachment multipart upload | mitigate | The `X-Atlassian-Token: no-check` header is already correctly implemented and is the official DC mechanism for bypassing XSRF on programmatic uploads (PATTERNS.md line 255). Existing test `add_attachment_sends_multipart_with_x_atlassian_token_header` (PATTERNS.md line 288) asserts header presence. Must NOT be removed by the fix per Pitfall 5. |
| T-05-19 | Path Traversal | download_attachment writing to dest_path | mitigate | The download destination is user-specified via the CLI args; the file content is server-supplied. The download path resolution does NOT use server-supplied path components for the local destination — only for the URL. No traversal vector. |
| T-05-20 | Resource Exhaustion | Large attachment download | accept | Existing `download_attachment` uses streaming via `bytes::Bytes`; no full-file in-memory buffering. Acceptable for a CLI tool. |
| T-05-21 | Information Disclosure | Local file content uploaded as attachment | accept | User-initiated action; the user is responsible for the file they upload. No unintended data exfiltration. |
</threat_model>
